# Local Max payment readiness

This is preparation for configuration and controlled provider testing. No live Stripe checkout, payment, deployment or release was performed. The desktop app's authenticated account and cross-device entitlement layer is still to be implemented by Claude.

Production handlers are `D:/atlias-site/server/entitlement.mjs` and `server/max-waitlist.mjs`; the older `server/billing.mjs` is a separate prototype. The supported offer remains $4 for the first paid month after launch, then $12 per month. Prelaunch time consumes no paid month.

Required launch configuration: `ATLIAS_MAX_RELEASED=true`, a charge-enabled live Stripe account, `STRIPE_SECRET_KEY`, an active live USD 1200 monthly `STRIPE_PRICE_ID`, a valid USD 800 once-only `STRIPE_INTRO_COUPON_ID` eligible for that product, `ENTITLEMENT_PRIVATE_KEY` (Ed25519 PKCS8 PEM), matching `ENTITLEMENT_PUBLIC_KEY` (base64 SPKI DER), `RESEND_API_KEY`, and `RESEND_FROM_EMAIL`. `SITE_URL` is optional. The release's immutable public key must equal this public key; test keys do not establish production alignment. Keep all real secret values outside reports and version control.

Stripe requests pin `2026-09-30.endive`. The official current OpenAPI schema was inspected and its SHA is recorded under `reports/ui-goal-1028/stripe-schema-evidence.json`. Paid invoices use `status=paid`; the removed `invoice.paid` boolean must not be required. [Official schema](https://raw.githubusercontent.com/stripe/openapi/master/openapi/spec3.json).

Checkout accepts a bounded POST body with a 64-character lowercase hex install id and a UUID v4 request id. Atlias persists the request id before sending, then stores the returned live Checkout Session id. A retry within 24 hours uses the same opaque Stripe idempotency key. Entitlement checks use that session receipt and the expanded subscription/latest invoice, avoiding subscription search's read-after-write delay. A legacy request without a receipt still uses subscription search and retains that consistency limitation. [Idempotency](https://docs.stripe.com/api/idempotent_requests), [search consistency](https://docs.stripe.com/api/subscriptions/search).

Access requires the expected live Max price, one item with quantity one, an active subscription, and a real live paid invoice. Open, expired and processing checkouts have separate responses. Signed passes last at most seven days and cannot exceed the paid-through date plus three days. Revocation removes the cached pass while preserving install identity and user work. Network failures permit only a still-valid signed offline pass. API errors do not expose Stripe's private messages.

The local contract integration test connects the actual client license module to the actual production handlers with an injected fake Stripe provider and generated test signing keys. It covers retries after a lost response, session-bound activation, signature verification, renewal, offline expiry, revocation, processing and expired checkout recovery. This proves the local contract, not actual Stripe account readiness, mail delivery, real settlement or production deployment.

Before a release: configure the real account and keys; compare the release public key; run controlled Stripe test-mode integration in a separately configured environment; verify checkout cancellation, delayed payment, renewal failure and cancellation against real provider events; then verify live configuration without creating an unauthorized charge. The current production readiness gate deliberately rejects test mode. macOS/Linux desktop packaging and authenticated Max access remain part of Claude's app work.
