# Atlias Max product workflows: Reason, Claude Code, and ChatGPT

## 1. What do primary sources actually establish?

### Takeaway

Use Claude Code's operational documentation for coding controls and ChatGPT's help documentation for approachable chat organization. Reason Machines is the strongest match for Gev's reference to "Reason," but that identity remains an inference; its public presentation is useful visual evidence, not a tested implementation contract.

Research verified on October 28, 2026, America/Chicago. Evidence classes used throughout: **Documented** means an official operational or policy document states the behavior; **Presented** means a vendor page or README advertises or demonstrates it; **Proposed** means an original Atlias adaptation. No competitor was installed, signed into, purchased, or exercised against a private account. No runtime feature in this note is independently tested. Public documentation is stronger than marketing for specifying intended behavior, but neither proves account availability or successful execution on Gev's PC or an iPhone.

### Cited Findings

- **Reason identity, strongest candidate:** Reason Machines explicitly calls Reason an AI teammate for work and code. Its public presentation shows sessions, a context composer, model labels, Review/Desktop/Terminal views, changed files, check summaries, and a mobile section. These are presented product examples, including a staged game-fix scenario, not independent evidence that a task passed. [Reason official product page](https://reasonmachines.com/).
- **Other names to keep separate:** Reason ONE AI advertises an iOS/Android product named Reason Home; that page does not establish a coding workspace. Reasonix's repository describes a different product, a DeepSeek-oriented coding agent. Neither establishes that Gev meant it. Do not silently substitute either product for Reason Machines. [Reason Home download page](https://reasonone.ai/pages/reason-home-app), [Reasonix repository](https://github.com/futureflowtech/reasonix).
- **Reason's limits and policy evidence:** The October 23 policy states that cloud messages, workspaces, attachments, and checkpoints are stored to support running and resuming sessions. Features identified as local execute on the device, while account, telemetry, inference, and integrations can still transmit data. It also describes requested OAuth scopes and provider terms when using one's own credentials. A local execution label therefore does not establish fully offline processing. [Reason privacy policy](https://reasonmachines.com/privacy-policy).
- **Reason's efficiency claims are not adopted:** The October 10 release article makes benchmark and cost comparisons. Those are vendor research claims requiring separate receipt review; they do not verify navigation, approvals, recovery, or native mobile operation. This note makes no comparative speed, quality, or cost claim for Atlias. [Reason Agent 1.1 announcement](https://reasonmachines.com/blog/introducing-reason-agent-1-1).
- **Claude Code desktop, documented:** Its composer supports file mentions and attachments; the desktop interface exposes a model and permission selector. It documents visual diffs and a supported route for resuming CLI sessions. Desktop and CLI keep separate session lists; transfer is explicit, with platform, authentication, and active-session restrictions. Do not equate shared configuration with automatically unified history. [Claude Code desktop documentation](https://code.claude.com/docs/en/desktop).
- **Claude Code conversation control, documented:** Messages entered while Claude works are queued; ordinary messages can enter after current tool calls, while commands are generally held until the turn ends. The queue can be taken back for editing. Esc interrupts without submitting the draft. Diff views distinguish working-tree changes from per-turn edits. [Interactive mode](https://code.claude.com/docs/en/interactive-mode).
- **Claude Code findability, documented:** The resume picker supports search, preview, rename, all-project/worktree filters, and branch filtering. Branching creates a separate conversation; it does not imply an isolated copy of the repository. Ambiguous names and failed resume operations have explicit outcomes. [Manage sessions](https://code.claude.com/docs/en/sessions).
- **Claude Code authority, documented:** Permission rules are enforced by the application, not by model instructions. Manual behavior differs by tool. Plan mode permits reading and read-only exploration commands, while blocking source edits. It must not be described as a mode that never runs commands. [Configure permissions](https://code.claude.com/docs/en/permissions).
- **Claude Code undo, documented with limits:** Checkpoints provide conversation/code restoration but do not cover every change. Files changed only through Bash, many subagent changes, and concurrent external edits can remain outside tracked restoration; linked files can be skipped. Checkpoints are not a replacement for Git history. [Checkpointing](https://code.claude.com/docs/en/checkpointing).
- **Claude Code usage, documented:** `/usage` separates session token estimates from subscription plan usage. Its dollar figure is not a subscriber's bill. If fetching plan usage fails, the client may show a recent cached reading labelled with its age; a fetch rate limit is distinct from an exhausted work allowance. [Manage costs effectively](https://code.claude.com/docs/en/costs).
- **ChatGPT organization, documented:** Projects group chats, sources, and instructions; project instructions apply within the project. Eligible chats can be moved into projects. The documentation supports continuation across devices, subject to plan and workspace availability. This does not imply that local source folders automatically sync. [Projects in ChatGPT](https://help.openai.com/en/articles/10169521-projects-in-chatgpt).
- **ChatGPT retrieval, documented:** Sidebar search is available on web, iOS, and Android. It searches existing account/workspace content, including chat titles/messages, with result types varying by account. Archived chats can be found; deleted chats cannot be recovered through search. Older chats missing from the recent sidebar are not necessarily deleted. [Finding chats, projects, and files](https://help.openai.com/en/articles/10056348-finding-your-chats-projects-and-files-in-chatgpt).
- **ChatGPT attachments, documented:** Supported documents, spreadsheets, presentations, images, and audio can be attached, with plan/model/client restrictions. The API has separate requirements. Storage and rolling upload limits are different, and failed uploads may count toward rate limits. Do not copy ChatGPT's file limits into Atlias without an Atlias backend contract. [Uploading files and audio](https://help.openai.com/en/articles/8555545-uploading-files-and-audio-to-chatgpt).
- **ChatGPT connected services, documented:** App availability depends on interface, account, plan, region, model, and workspace policy. App mentions and the composer menu are documented entry points; connecting an account and approving an individual operation are distinct steps. [Connected apps](https://help.openai.com/en/articles/11487775-connected-apps-in-chatgpt).
- **ChatGPT approvals, documented:** App permission settings do not grant new provider access. An approval card describes the app and proposed action; available approval persistence varies. Saved permission does not override workspace restrictions, provider rights, or safety protections. [Managing app permissions](https://help.openai.com/en/articles/20001495-managing-app-permissions-in-chatgpt).
- **ChatGPT recovery, documented:** Troubleshooting distinguishes network/local configuration issues and service incidents. For stuck generation it documents Stop generating and Regenerate. This establishes a user-facing interruption/retry workflow, not exactly-once execution or an offline mode. [Troubleshooting error messages](https://help.openai.com/en/articles/7996703-troubleshooting-chatgpt-error-messages).

### Inferences

- The strongest reference blend is ChatGPT's project/chat discoverability plus Claude Code's concrete tool, permission, and review controls. Reason's coherent session-to-result presentation can inform layout without importing its cloud architecture, autonomous publishing, or marketing claims.
- Reason Machines is likely the intended Reason because its stated coding/chat workflows align with Gev's task. No source links Gev's utterance to that vendor, so label the reference provisionally in the build brief.
- Apply RESEARCH-FIRST lines H4 and H5: stopping differs from completing; a model's success statement differs from a check result. This is a product state requirement, not an instruction to change the harness here. [Local research handbook](D:/harness-work/atlias-evolve/RESEARCH-FIRST.md).

### Gaps

- No public Reason operational manual or source implementation for queue, approval, history search, cancellation, quota rollover, or offline recovery was found in the focused search. Absence from this search is not proof the feature is absent.
- Reason's public mobile section does not prove iOS App Store availability, a native Windows client, simulator results, signing, device execution, or feature parity.
- Local project research searches did not surface a usable local ChatGPT product reference; official OpenAI help pages were used as the permitted fallback. No private ChatGPT chats or account pages were collected.
- All web pages are mutable. Links and retrieval date are supplied, but these notes are not an archived release snapshot. Screenshots on a vendor page do not establish responsive behavior or accessibility.

## 2. Which workflows should Atlias adapt, with what evidence?

### Takeaway

The primary beginner workflow should be: choose a project, reopen or start a chat, confirm the engine/account, describe the task with context, follow progress, resolve any approval, inspect changes/checks, and continue later. Each visible control must correspond to an actual backend capability.

### Cited Findings

### Inferences

- Use progressive disclosure: chat/task text first, compact tool summaries second, expandable technical detail. Keep approvals and failures prominent because they require a decision.
- Desktop can show navigation, conversation, and optional review panes together. On iOS, preserve the same chat/run identity while presenting those views sequentially. This is a design recommendation, not a simulator-tested layout.
- A shared entitlement named Max is independent from the engine's subscription/account allowance. Avoid showing an Atlias Max badge as proof that a provider has available quota or that provider usage is included.
- Source permissions and execution permissions are separate concepts. A connected repository or file attachment is context access, not authorization to deploy, publish, purchase, or send messages.

### Gaps

- The backend's event ordering, cancellation acknowledgment, replay support, exact tool permission scopes, attachment ingestion, and engine-specific session resumption need implementation inspection by Claude. The research did not inspect or change app code.
- No competitor source above establishes exactly-once external actions after reconnect, reliable automatic engine rollover, identical search across all clients, or lossless full-code undo.

### Inferences

All items below are **Proposed implementation and acceptance criteria**, not competitor facts or current Atlias capability claims.

1. **P0: one trustworthy session loop.** Select an existing local project; start a chat; send text plus a supported attachment; see an actual streamed response/tool event; stop an active run; reopen the same chat after app restart. Acceptance: the draft, attachment identity, project, engine/account, message order, and run state survive. A click that only changes UI is insufficient.
2. **P0: durable history and searchable resume.** Store stable session/run/message identifiers and search the full saved set, not just the sidebar cache. Acceptance: a chat beyond the recent-page limit, renamed chat, archived chat, non-ASCII filename, and two chats with the same title remain distinguishable and resumable. A failed resume preserves the currently open chat.
3. **P0: explicit run state.** Derive state from backend events rather than a spinner timer or assistant prose. Acceptance: cancellation races with a final event do not create two completions; late events cannot revive a stopped run; duplicate reconnect events do not duplicate messages. "Stop requested" remains visible until acknowledged or failed.
4. **P0: approvals and selected account.** Bind each approval to a run, tool request, and account. Acceptance: Deny prevents the action; approve-once authorizes one intended request; an account switch invalidates an approval targeting the old account; reconnected screens do not resubmit approval. Follow Gev's existing subscription-switch exception exactly.
5. **P0: inspectable output and real checks.** Render actual file changes and check receipts. Acceptance: failed, cancelled, stale, skipped, and never-run checks cannot show as passed. Read-only/no-change tasks are valid outcomes; absence of a diff is not a failure. A successful chat reply is not proof of successful edits.
6. **P0: truthful account/allowance presentation.** Show provider data and its age; label unavailable/stale state. Acceptance: no reading is not 0%; a stale 99% reading does not silently become fresh; reset countdown uses the actual timestamp/time zone; fetching usage failing does not become "plan exhausted." Do not silently use another subscription or paid API credits.
7. **P0: disconnection and retry.** Preserve drafts and local transcript data, then query actual run state when the backend returns. Acceptance: lose network during streaming, tool execution, and approval; reconnect without replaying a tool mutation. If the action outcome is unknown, say so and request reconciliation rather than automatically sending the same side effect again.
8. **P0: Max entitlement.** Enforce access using the actual entitlement source, not only a hidden navigation item. Acceptance: valid Max, expired Max, unavailable entitlement server, sign-out, account switching, and pending purchase each have distinct truthful behavior. Test any billing integration in the appropriate local/test environment only; no charges or launch promises are authorized by these notes.
9. **P1: useful queue and plan mode.** Add these only over backend semantics already implemented or deliberately specified. Acceptance: edit/remove queued items before delivery; show consumed items separately; queued attachments retain their submitted version; Plan cannot edit through a secondary tool path. Do not pretend a queue is implemented if it is merely a draft list.
10. **P1: mobile continuity and daily use.** Offer accessible touch controls, keyboard-safe composer, readable code/diffs, voice only if supported, copy/share controls with explicit scope, and clear navigation back to the same task. Acceptance: long messages, large text settings, on-screen keyboard, long filenames, interruption/backgrounding, and return from another screen preserve the draft and active run.
11. **P1: constrained recovery.** If implementing checkpoints/undo, display which paths and actions can actually be restored. Acceptance: external edits, concurrent sessions, shell-only changes, binary files, and unsupported linked paths cannot be advertised as fully reversible. Conversation branching and repository branching remain distinct controls.
12. **Completion evidence, two passes.** Functional pass: exercise supported end-to-end workflows and retain commands/results or recordings. Adversarial pass: independently inspect all changed files and exercise the race/failure cases above. Windows build/run, iOS simulator build/run, physical iPhone run, signing, and distribution are separate receipts. Report each tested/untested status explicitly; a web preview or successful JavaScript check proves none of the missing native steps. Do not use `tsc` under Gev's standing instruction.
