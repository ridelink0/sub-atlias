# Build Atlias Max Around Trustworthy Workflows

**Build one Max-exclusive desktop app for macOS, Windows and Linux, with the real Atlias harness executing local tools on each operating system.** Gev's final desktop scope supersedes the earlier mobile recommendation. The practical starting stack is Electron, a shared React interface, a narrow preload bridge and the existing Node harness in a supervised utility process. ChatGPT supplies useful project/history organization, Claude Code supplies concrete permission and change-review workflows, and Reason Machines supplies tentative visual inspiration whose staged homepage remains marketing evidence. The implementation must expose every actual Atlias capability through an audited capability inventory, then prove complete workflows before styling. Existing paid Max activation and local Stripe contract tests provide a licensing baseline; authenticated account ownership and independently revocable desktop installations remain to build. **This brief recommends an implementation and acceptance contract; it does not certify an app, live billing, platform parity, signing or release readiness.** ([Authoritative build goal](<D:/atlias-app/docs/CLAUDE-APP-HANDOFF-1028.md>), [Corrected desktop architecture](<D:/atlias-app/research_notes/Atlias Max app research/platform_architecture.md>))

## One session loop should organize every real Atlias capability

The beginner path should remain understandable from first launch to a resumed task: sign in and resolve Max, open a project, start or find a chat, confirm the engine/account and local project, describe the task with supported context, follow activity, answer a specific approval or blocker, inspect changes and checks, and reopen the same task later. ChatGPT documents grouping chats, sources and instructions in projects; its search documentation distinguishes searchable history from a short recent list. Claude Code documents attachments, file mentions, model and permission controls, diffs and explicit routes between desktop and CLI sessions. These references support the sequence, not a universal session format or automatic source-folder synchronization. ([ChatGPT projects](https://help.openai.com/en/articles/10169521-projects-in-chatgpt), [ChatGPT search](https://help.openai.com/en/articles/10056348-finding-your-chats-projects-and-files-in-chatgpt), [Claude Code desktop](https://code.claude.com/docs/en/desktop))

**The scope is the complete real Atlias feature set.** Before building screens, Claude should inspect current tool registries, commands, engine adapters, session stores, permissions, settings and documentation, and create a traceability ledger. For every real feature, record its backend entry point/schema, dependency, credential source, permission class, Windows/macOS/Linux behavior, interface, cancellation/resume support, limitation and receipt. Include memory/knowledge, skills, MCP integrations, workers, customization and other subsystems wherever the current implementation actually supports them; this research has not source-audited those contracts and does not certify an invented list. A host capability manifest should drive availability. A missing adapter is unfinished scope rather than a successful-looking control. Delivery priorities sequence the work without removing capabilities from Gev's goal. The local research's H3, H4 and H5 require visible tool failures, distinct stopping/completion states and mechanical verification. ([Atlias research rules](<D:/harness-work/atlias-evolve/RESEARCH-FIRST.md>), [Build goal](<D:/atlias-app/docs/CLAUDE-APP-HANDOFF-1028.md>))

| Workflow | Proposed implementation contract | Acceptance condition |
|---|---|---|
| Projects and chats | Stable project/session/message/run IDs, visible local execution target, New chat and return path | Switching projects preserves each draft and never changes an active run's target. Long/duplicate names remain distinguishable. |
| Search and resume | Full saved-history title/message search, project/engine filters and preview; separate recent navigation | A chat beyond the recent-page limit, renamed/archived chat and identically named chats remain findable and resumable. Failed resume preserves the open chat. |

## A shared desktop interface should isolate each local harness

**Recommend Electron with React, a narrow preload bridge and a supervised Node utility host.** Electron supports the three target operating systems and utilityProcess provides a Node-enabled process with messaging, directly fitting the existing JavaScript harness. Native Node dependencies still need Electron-ABI and architecture checks. Share the application state, validation, UI and protocol; keep OS-specific executable discovery, shell/PTY behavior, process ownership, credential storage, permissions and filesystem identity behind explicit adapters. No size, performance, startup, reuse percentage or delivery estimate was measured. ([Electron platforms](https://github.com/electron/electron#platform-support), [Process model](https://www.electronjs.org/docs/latest/tutorial/process-model), [Utility process](https://www.electronjs.org/docs/latest/api/utility-process), [Native modules](https://www.electronjs.org/docs/latest/tutorial/using-native-node-modules))

Tauri 2 is viable, but retaining this harness still requires a packaged Node sidecar/runtime and introduces Rust supervision/IPC plus different WebViews and Linux dependencies. React Native macOS and Windows have separate native setups and do not establish a matching Linux target. Electron is the smallest practical integration recommendation for this scope, subject to a real dependency spike. If a dependency requires standalone Node, prove and explicitly package/version it rather than silently finding arbitrary PATH Node. Do not switch frameworks automatically when a spike fails; document the actual adapter gap first. ([Tauri Node sidecar](https://v2.tauri.app/learn/sidecar-nodejs/), [Tauri capabilities](https://v2.tauri.app/security/capabilities/), [Tauri prerequisites](https://v2.tauri.app/start/prerequisites/), [React Native macOS](https://microsoft.github.io/react-native-macos/docs/getting-started), [React Native Windows](https://microsoft.github.io/react-native-windows/docs/getting-started/))

| Boundary | Proposed responsibility | Required separation |
|---|---|---|
| React renderer | Projects, conversation, activity, review, approvals, usage, search and settings | No Node, filesystem, shell, generic IPC or provider secrets |
| Preload | Filtered method for each supported application operation | No raw ipcRenderer, arbitrary channels, event objects or unrestricted paths |
| Electron main | Window/dialog lifecycle, IPC sender checks, account/device state, secret adapter and utility supervision | No unvalidated renderer commands |
| Utility host | Existing Atlias harness/tools/providers, project scope, jobs/events, approvals, cancellation and receipts | No public execution endpoint or renderer-chosen credential paths |
| OS adapters | Executables, PTY/shell, process trees, OS permissions and file identity | No guessed platform fallback reported as successful execution |
| Account service | Authenticated identity, server-derived Max, independent installation issuance/revocation | No provider tokens merely to prove membership; no private signing keys in clients |

Bundle the UI under a tightly scoped app protocol. Keep nodeIntegration off, contextIsolation on, renderer sandbox on and webSecurity on. Treat model output, markdown, repository content, diffs and tool output as untrusted; sanitize rendered HTML, block scripts and constrain navigation, new windows and external URLs. Every privileged handler must validate sender frame/origin, schema, size and current account/project/job authority. Expose named operations such as listSessions, resumeSession, startJob, cancelJob and decideApproval rather than a generic command or filesystem bridge. Packaging fuses should disable unused capabilities before signing, based on the selected runtime's actual needs. ([Electron security](https://www.electronjs.org/docs/latest/tutorial/security), [Context isolation](https://www.electronjs.org/docs/latest/tutorial/context-isolation/), [Sandbox](https://www.electronjs.org/docs/latest/tutorial/sandbox), [Fuses](https://www.electronjs.org/docs/latest/tutorial/fuses))

**The utility host intentionally has local user authority; process separation is not an OS sandbox for arbitrary shell commands.** Renderer sandboxing cannot certify shell containment, and string inspection cannot bound every shell side effect. Preserve and verify the harness's real authority controls. Prefer MessagePorts/private stdio; this desktop scope needs no mandatory remote execution relay. If existing loopback transport is retained, bind loopback only and require authentication and origin/host validation. Project IDs should map to canonical selected roots with symlink/junction, permission and external-edit conflict checks. Use declared executables and arguments with OS-aware spawning rather than unsafe string concatenation. ([Process privileges](https://www.electronjs.org/docs/latest/tutorial/process-model), [Utility messaging](https://www.electronjs.org/docs/latest/api/utility-process), [Node child processes](https://nodejs.org/api/child_process.html))

Persist stable request IDs and immutable payload hashes before mutation. A repeated key/payload recovers the existing job; changed payload under that key fails. Journal ordered bounded events and artifacts independently of UI attachment, then restore snapshot/cursor state after reconnect. Separate UI close, app quit and explicit cancellation, with a visible policy for in-flight work. Cancellation remains requested/stopping until the host supplies evidence, then reconciles late completion and final usage. Windows Job Objects require descendant/breakaway tests; macOS/Linux process groups require their own native proof. Preserve unrelated user processes. MCP resumption is protocol-version-dependent, so pin the installed contract and keep durable app jobs above transport without migrating MCP merely for the UI. ([Windows Job Objects](https://learn.microsoft.com/en-us/windows/win32/procthread/job-objects), [Node processes](https://nodejs.org/api/child_process.html), [MCP lifecycle](https://go.sdk.modelcontextprotocol.io/protocol/))

## Conclusion

The useful product boundary is an inspectable task identity: Gev should always be able to see which local project and provider account own the work, what authority was granted, what changed and which check supports the outcome. Sharing that model across desktops improves continuity without silently transferring secrets or confusing account membership with machine access.

Claude's first integration should be judged by whether one real task survives account resolution, execution, interruption and review with evidence intact. That exposes missing contracts before a polished interface hides them. Completion then becomes an auditable coverage decision across actual tools and supported operating systems, rather than a model's final message or a count of finished screens.
